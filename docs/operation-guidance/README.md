# 操作指引模板使用说明

这些是[已确认规范](../operation-guidance.md)的配套编写模板。功能内容已接入离线阅读，实际目录、字段和入口参见[实现契约](implementation-contract.md)。包含占位文字的模板不进入安装包；版本绑定与同源发布正文已接入发布工具。

## 功能指引

复制 [feature.template.json](feature.template.json)，替换标识、标题、用途、入口、步骤与结果。只列实际适用的平台；当前模板的 `darwin` 是 macOS 示例，并不表示其他功能仅支持 macOS。

首批必备功能由 [manifest.json](../../content/guidance/manifest.json) 按稳定 ID 登记，对应文件名为 `content/guidance/features/<ID>.json`。增加、拆分或移除这批正文时同步维护清单；检查器会指出未被本次发布说明引用的缺文件或无效正文。清单或正文有问题只报告警告，不阻断构建与发布。

准备条件与常见问题的 `items` 有内容时，`notApplicableReason` 留空。确实不适用时清空 `items` 并填写具体原因；二者都空视为未编写。

图片按需放入受控仓库资源目录；在相应步骤增加以下对象，路径只是格式示例，不是已存在的截图：

```json
{
  "image": {
    "src": "assets/example-step.png",
    "alt": "说明图片中与本步操作有关的内容",
    "caption": "按需填写图片补充说明"
  }
}
```

`entry.target` 与 `placements` 必须使用实现中已经登记的标识。不要填写 URL、系统路径、脚本或页面源码表达式；复杂对象背景交由受控入口处理。

## 发布说明

有操作变化用 [release-changed.template.json](release-changed.template.json)，没有操作变化用 [release-none.template.json](release-none.template.json)。每次发布必须二选一编写实际内容；不能通过选择 `none` 绕过未编写的操作说明。

人工核对部分据实填写，不自动填写用户身份或通过结果。下面是字段形式示例，仍含占位文字：

```json
{
  "review": {
    "status": "completed-with-gaps",
    "reviewer": "实际核对人",
    "checkedAt": "实际核对时间（含时区）",
    "source": "实际核对的源码 SHA 或版本",
    "environment": "实际运行平台、安装版或开发版、隔离资料情况",
    "checks": [
      {
        "guideId": "实际指引标识",
        "stepIds": ["实际步骤标识"],
        "result": "not-verified",
        "evidence": "说明未验证原因；已验证时记录相应证据"
      }
    ],
    "knownGaps": ["实际缺项及后续处理方式"]
  }
}
```

建议状态词：核对整体使用 `pending`、`completed`、`completed-with-gaps`；单项结果使用 `passed`、`failed`、`not-verified`、`not-applicable`。`completed` 不能覆盖尚未检查或失败的项目，`not-applicable` 必须说明原因。状态词是机器字段，面向用户显示中文。

维护者不必预填正式版本号。发布准备从实际版本计划产生版本和源码绑定；已有版本重跑始终使用该 tag 的记录。`review.source` 是实际核对来源，与生成的发布绑定分开保留；两者有差异时重新核对，不能自动篡改核对证据。

## 发布前核对清单

编辑时可以只检查当前工作区，不需要安装其他 Node 依赖：

```sh
node scripts/check-operation-guidance.mjs --output release/guidance-check.json
```

也可运行 `npm run guidance:check`。此命令读取当前目录的 `content/guidance`，只输出诊断和可选报告，不创建提交、标签或 Release。报告保留所有可用正文、核对记录、图片路径和警告。坏 JSON、缺少待发布说明、图片或引用以及核对缺项都以退出码 0 报告；参数错误、检查程序本身错误与报告写入失败仍按错误退出。

真正的发布预览使用 `./发布新版本.command --dry-run`：它检查隔离检出的远端 master，不采用当前工作区未提交或未推送的修正。终端显示实际选定的用户摘要、变化关联、核对状态和每条警告的文件、字段、原因及修正建议。确认发布时仍使用同一检查；内容警告不增加一次确认，也不替代正常的构建与包安全检查。

GitHub Actions 在 tag/version 核验后、依赖安装和打包前调用同一个 Node 检查入口，输出 warning 注解和步骤摘要，并在 `release-verification` 产物中保存 `guidance-check.json`。没有未处理警告不等于维护者已经列全用户变化；必须继续人工核对下面的清单。

`--directory` 可指定已检出的其他源码，`--source` 为报告记录业务源码，`--release-tag` 检查该 tag 对应的绑定记录（省略时检查 `pending.json`）。指定 tag 且不填 source 时，从当前固定 tag 的版本提交恢复信息读取业务源码，并核对 tag、父提交、版本文件和允许变更范围；CI 使用这一方式。这些参数不执行 Git 拉取或版本绑定。核对记录中的来源不自动改写，来源不一致时报告警告并要求重新核对差异。

发布准备只使用已提交的待发布说明，生成对应版本的绑定记录；失败换号可重新绑定，同一 tag 重跑不能采用后改的 pending。GitHub 正文显示绑定摘要、应用内查阅路径及固定版本来源链接，并保留技术提交和构建来源。下一次版本准备通过 GitHub 正式发布状态与原 tag 内容确认历史，缺失与失败记录不伪装成已发布版本；已经发布的包保持不变。

- [ ] 对比本次实际发布源码，列出用户可见操作变化。
- [ ] 为每项变化关联有效功能指引；无变化则写明原因。
- [ ] 首批逐项覆盖全部现有功能，包含次要菜单和失败／取消路径。
- [ ] 使用隔离示例资料核对入口、步骤、结果、平台和截图。
- [ ] 检查密码、备份、导出、删除与更新术语，避免承诺不存在的恢复能力。
- [ ] 检查历史引用、当前入口、图片替代文字及离线资源。
- [ ] 记录核对来源、环境、结果、证据和所有已知缺项。
- [ ] 确认内容及图片已经随源码提交到计划发布的远端提交。
- [ ] 查看本地与 CI 指引警告，确认 GitHub 摘要和安装包内容来源一致。

本清单规定编写与核对责任，尚未勾选或存在问题也不新增发布阻断；仍应如实保留警告及未完成记录。

桌面回归从被测安装包自身的原始指引内容判断正常显示或降级分支。正文无效时必须验证“暂不可用”和正常关闭，入口失效时必须验证禁止导航，缺图时必须验证替代文字；不直接跳过所有指引测试。降级用例的报告会注明未覆盖的正常路径，不能用这类通过结果替代首批内容核验。真正的代码、IPC、保存保护或导航实现失败仍应使对应行为测试失败。
