# v0.1.17 真实下载中断调查与修复讨论

状态：事实调查与 Q1–Q12 完整方案已由维护者于 2026-10-29 确认；源码修复见[实施记录](download-reliability-implementation.md)，新版本尚未发布。日期：2026-10-29。

## 已观察到的结果

- 从已发布的 v0.1.15 macOS 安装包，以隔离应用和资料检查私有仓库的 v0.1.17 Release 成功。第一次真实 ZIP 下载约 9 MB 后，流读取返回 `net::ERR_HTTP2_PROTOCOL_ERROR`；更新历史在下载 271428 毫秒后记为失败，本次暂存 ZIP 已清理。安装、备份和健康确认没有开始。
- 在相同版本对和正式 Release 上重试，下载与完整校验成功。原验收脚本随后仍按旧“主密码”规则断言，而应用已要求独立备份密码；该失败属于验收脚本过期，不是下载失败。
- 将**隔离的验收脚本副本**改为设置独立备份密码后，真实 GitHub 下载约 19 秒完成；保留的 130390531 字节 ZIP 的 SHA-256 为 `63fc9ac99e488e497ee4dea1dfdbe90806a590a96ce4984d3c8e52a15bf742ab`，与正式 Release 一致。安装前加密备份、原位置替换、quarantine 保留和旧包备份恢复通过。新版在临时隔离位置未得到健康回执，安装助手明确记录 `needs-attention:health-timeout`，属于人工处理结果，不能称为无人值守健康成功。
- 对同一正式 ZIP 请求前 12 MiB，代理链路下 HTTP/2 与 HTTP/1.1 均返回 `206` 和预期字节数。这个对照不支持“HTTP/2 永远无法访问该资产”的结论，也不能排除偶发的代理、CDN 或 Chromium 连接问题。

## 代码边界与原因判断

`v0.1.15` 和 `v0.1.17` 的 `electron/update.ts`、`electron/update-fetch.ts` Git 文件对象相同。旧安装版因此无法从新 Release 自动获得新的下载逻辑。当前流程先读取 SHA256SUMS，再经固定 GitHub API 获取 ZIP；只有固定 API 请求携带授权，校验跳转后从 CDN 流式读取正文。下载已经开始后，`reader.read()` 的错误会直接上抛；协调器清理整个暂存目录并显示原始错误，**没有有限重试或断点续传**。

错误码只表明 Chromium 的 HTTP/2 流发生协议错误，不能仅凭它判定是哪一方造成的。后续同一资产下载成功，说明 Release、凭据和包内容并非稳定地不可用。产品侧已确认的可靠性缺口是：一次可恢复的传输中断直接变成用户必须从头下载的失败，且提示没有说明下一步。

更新中的“版本发现”“下载并校验”“安装前备份与替换”“新版健康确认”是不同结果。此次第一次仅版本发现通过；后续隔离重试到达了明确的人工处理结果。两次测试不可合并称为一次自动健康升级。

## 已确认的方向

1. 旧安装版用户提供正式 DMG 的人工过渡步骤；新版另行修复未来的自动下载。人工安装不得删除现有资料。
2. 可恢复的网络错误有限自动重试；授权、来源、版本、散列或应用包校验失败不能作为网络错误继续重试。最终完整校验始终是安装前提。
3. 仅在服务器对同一资产返回可核对的部分响应时续传；否则安全地从头下载。
4. 更新历史只保留本机脱敏诊断，如阶段、已下载字节、错误码和重试次数；不保存授权头或带签名参数的私有下载地址。
5. 同一目标版本的未完成片段可跨应用重启保留最多 24 小时；版本变化、取消、校验失败或安装成功时清理，不将片段视为回滚包。
6. 一个下载任务最多 3 次自动尝试，重试间隔逐步增加；只重试网络中断及可恢复的服务错误。用户始终可以取消或手动重试。
7. 重试耗尽后说明失败阶段和已下载进度，并提供重新下载及查看正式 Release 的人工安装入口。
8. 下一版应强化真实私有 GitHub 更新验收，区分健康启动与 macOS 明确的人工处理结果。
9. 持续有进度时不沿用单次请求的 10 分钟总超时；连续约 2 分钟没有新数据才判定停滞，整个下载任务最多约 2 小时。达到总上限后，符合条件的片段仍可在 24 小时期限内供手动继续。
10. 采用两段式验收：公开前验证固定安装包与可控断流；公开后立即用隔离旧版和真实私有 GitHub 资产验证目标版本。发布说明分别写明两阶段的实际结果。
11. 公开后若发现可复现的资料损坏或安装风险，暂停该版作为自动更新目标并公告，再发布新版本号修复；普通可恢复网络问题记录已知限制和手动路径，不重写已发布标签或资产。

当前客户端只读取固定仓库的正式 latest；Draft 不可作为无替身真实更新目标。完整方案确认后，以 [ADR 0015](../../docs/adr/0015-recover-release-downloads-with-verified-resume.md) 和 [ADR 0016](../../docs/adr/0016-verify-real-github-updates-after-publication.md) 作为后续规格与实施依据。

## 拟实施顺序

1. **旧版过渡**：为 v0.1.15 等已安装旧版写明从正式 Release 下载 DMG、核对 SHA-256、先备份、退出应用、在 Finder 替换当前安装位置并按系统提示授权的步骤。保留现有资料；这不能倒装旧版自动下载逻辑。
2. **下载器**：把可恢复传输错误、授权／来源错误与完整性错误分开。每个任务最多三次尝试，逐步延长等待；取消立即停止。每次重新访问私有资产 API 并检查重定向，不能沿用过期签名 URL，也不能将授权发送到 CDN。
3. **受控续传**：未完成片段及不含秘密的目标身份记录放在受控临时目录。重启后只接受同一版本、资产身份、大小与期限内的普通文件；以请求范围和响应 `206`／`Content-Range` 核对续传起点，`200`、无效范围或无法确认的响应回到全量下载。任何拼接结果都必须重新计算完整 SHA-256，并通过现有应用包校验。
4. **反馈**：下载时展示总进度、当前尝试和已恢复字节；失败时展示可操作的说明和手动入口，底层错误码放在本机脱敏诊断中。下载就绪仍由用户选择立即或稍后安装，不把下载完成写成健康成功。
5. **验证与发布**：先用秒级中途断流、206／200／416、重启恢复、超时、取消、错误分类和凭据边界的用例将当前红探针变绿；再跑 macOS 安装版和固定包验证。发布后立即做真实私有 GitHub 旧版到新版隔离升级，分别报告健康或人工处理。

## 验证方法与资料

- 原始真实网络入口：`node scripts/verify-installed-update.mjs --github <已校验的旧版 App> 0.1.17`。它可抓到下载阶段错误，但当前脚本的备份密码断言需要修订；不能将断言失败误报为产品安装失败。
- 调查时将临时探针放入 `tests/update-retry-probe.test.ts` 并执行 `./node_modules/.bin/vitest run tests/update-retry-probe.test.ts`：固定 Release 的第一次正文流中途抛出同一错误、第二次返回完整 ZIP。当前实现约 0.2 秒内稳定失败，预期 `ready`、实际 `error`。临时探针在记录结果后已清理；实施时应将这一模式写入正式回归，而不能把该红结果算作通过。
- 将中途断流纳入可控的 Electron 下载夹具，在秒级触发读取失败，分别验证安全重试、部分响应校验、全量散列、暂存清理及脱敏记录。现有本地 302 夹具和内存响应不覆盖这一故障。
- 修复后的真实验收仍须使用已发布旧安装版、私有 GitHub 资产和隔离资料，分别报告网络、安装、macOS 人工处理与健康结果。
