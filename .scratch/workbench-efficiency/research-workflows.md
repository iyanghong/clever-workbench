# 工作流与资料复用：开源参考调查

调查日期：2026-10-19。本文是讨论材料；候选方案均未获实施确认，不修改领域定义或架构决策。

## 工作台已有的基础

已阅读根目录 `AGENTS.md`、`CONTEXT.md`、问题跟踪与领域文档约定，以及 ADR 0001、0003、0004、0007。当前产品是技术负责人的单人本地工作空间；技术台账、工作任务、技术文档已经共享系统背景，凭据按需解锁。工作任务只可归属于系统；工作回顾中的“回顾跨度”是日历时间，不能称为实际工时。

代码已有以下能力，不能作为待开发的新功能重复建议：

- 访问入口能选择地址并打开，也能复制用户名和按需解锁的凭据。见 [AccessActions.tsx](../../src/features/ledger/AccessActions.tsx)。
- 系统、环境和资源详情能创建文档、创建任务及查看相关记录。见 [RelatedWork.tsx](../../src/features/ledger/RelatedWork.tsx)。
- 文档已有归属、正文搜索和自动保存。见 [DocumentsPage.tsx](../../src/features/documents/DocumentsPage.tsx)。
- 工作台已有工作回顾和可阅读系统资料包。见 [TaskWorkspace.tsx](../../src/features/tasks/TaskWorkspace.tsx)、[SystemExportDialog.tsx](../../src/features/ledger/SystemExportDialog.tsx)。

## 候选方案及取舍

以下是结合现有产品作出的判断；节省步骤是待用户验证的场景假设，没有测量到节省分钟数。

### 1. 参数化常用命令与文本

假设用户经常从旧文档找命令，再修改服务器地址、端口、日期或服务名称。可增加模板工具：选一条常用文本，选系统或环境作为本次输入，从台账带入公开字段，补齐参数后预览并复制。工具仍是全局工具，所选系统只是输入，不改变工具归属。

例如“查询某服务近 30 分钟日志”：原来需要找旧笔记、找到目标地址、替换多处参数、检查是否混入其他环境；改为选模板和目标，预览一次后复制。第一版只覆盖用户确实反复使用的几条命令，不做脚本市场或通用自动化引擎。

建议内置参数化与台账取值能力。若需求只是跨应用展开固定短语，直接使用 Espanso 更合适，工作台无需重做全系统键盘监听。首版不默认把凭据写入普通模板或历史；这符合 ADR 0004。是否需要直接执行命令，应另行确认执行环境和实际使用频率。

最关键的访谈问题：上周反复查找、修改并复制过的三段命令或文字分别是什么？它们变化的是地址、环境、日期，还是内容本身？

### 2. 从已完成任务沉淀排障记录，并复用文档模板

假设用户处理问题时已经在任务正文记下现象和过程，但之后仍需重新开文档、复制内容、选择系统并补结构。可在任务详情提供“整理为文档”，带入标题、系统和来源任务，由用户补齐“现象、原因、处理、验证”；也可从排障、上线检查、交接等少量模板新建文档。

Trilium 的可借鉴点是复用内容结构与引用，工作台不必再嵌入一套独立笔记应用。建议作为现有任务、文档功能内置。任务记录保留，生成的文档是用户整理过的技术资料；同一通用方法需要在多个系统查看时，可先做相关文档引用，避免复制多份。通用文档与系统文档仍按现有定义归属，不擅自改成多系统归属。

此方案省掉重新创建和拷贝背景的步骤，但只有“经常处理重复问题，现有记录难以复用”时才值得优先做。不要因为任务完成就自动生成大量空文档。

最关键的访谈问题：最近一次“这个问题以前处理过，但找不到怎么解决的”是什么？当时的过程记在任务、聊天、个人文档还是完全没记？

### 3. 从系统台账直达运行状态与排障背景

假设用户有一台始终运行且能访问目标网络的机器，可在那里部署 Uptime Kuma，再把状态页或对应监测页面保存为工作台的访问入口。先利用已有“打开入口”；若实际使用证明切换频繁，再考虑在系统详情加入状态摘要及“记录为工作任务”的动作。

建议外部部署与链接打开优先。桌面会退出、休眠或离开内网，因此自建桌面持续监测无法可靠替代常驻监测服务。单纯增加一个访问入口已由现有能力覆盖，不应包装成一轮新开发。状态摘要的认证、接口稳定性、网络可达性尚未调查，当前不能承诺可无缝接入。

监测告警是系统运行线索，不能默认等于用户的工作任务。发现异常后由用户选择是否立项，仍以系统为任务唯一归属，不把运行作业与个人任务混用。

最关键的访谈问题：现在最常见的是“故障没人提醒”，还是“已经知道故障，但找监控地址、账号和处理办法太慢”？前者应优先完善监测，后者更适合优化工作台入口。

### 4. 周回顾草稿与活动线索

先从已有任务的开始、完成时间和系统归属整理本周完成、未完成及补充说明，输出可编辑的周回顾草稿。若用户最头疼的是忘记记录临时工作，再评估从 ActivityWatch 导入当天活动摘要，作为人工补记的线索。

建议“从已有记录生成草稿”内置，“采集全机活动”留给 ActivityWatch。无需先重做窗口监测器。ActivityWatch 的原始窗口标题、网址不直接等同于做了什么工作，更不能把它们相加后覆盖工作台的回顾跨度或宣称精确工时。导入若进入实施阶段，应先让用户选择范围，保持本地处理并排除不需要的标题和网址；官方也建议向外部模型使用数据前先在本地聚合和删减。[官方导出说明](https://docs.activitywatch.net/en/latest/features/exporting-data.html)

最关键的访谈问题：写周报最费力的是忘记发生过什么、把已有记录重新组织措辞，还是需要精确统计工时？这三类问题需要不同方案。

## 当前优先判断

在不知道用户每周真实工作分布之前，只能给条件排序：若频繁复制修改命令，先做方案 1；若重复排障和交接占比高，先做方案 2；若周报整理负担明显，方案 4 的纯任务版可能更小且更快见效。方案 3 先用现有入口连接外部监测，不先立新工具项目。

本轮没有证明需要再做完整 API 客户端、知识库、监测平台或全系统文本扩展器，因此没有把这些加入自建清单。下一步应请用户讲最近一周的具体重复操作，再选一个最高频流程继续访谈。
